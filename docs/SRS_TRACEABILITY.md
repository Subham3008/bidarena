# BidArena SRS Traceability

## Source status and traceability integrity

`BIDARENA.md` is the only available requirements source in this workspace. It describes the product capabilities, ownership model, architecture constraints, required verification, and future delivery workflow.

`BIDARENA.md` also refers to a separate `BIDARENA_SRS.pdf` and requires traceability for `FR-1` through `FR-24`, `NFR 4.1` through `NFR 4.13`, `S-1` through `S-15`, and `SG-1` through `SG-15`. That PDF is not present. The official wording, acceptance criteria, priority, and intended ownership of those numbered requirements therefore cannot be verified and must not be invented.

This document uses two deliberately separate registries:

1. The official identifiers are recorded as `Blocked` until their source wording is available.
2. Requirements that are explicitly available in `BIDARENA.md` are tracked with local derived identifiers: `DA-*`, `DB-*`, `SI-*`, and `VT-*`.

Derived identifiers are planning aids, not substitutes for official SRS identifiers. When the source PDF becomes available, each official requirement must be mapped to one or more derived requirements using its exact wording.

## Status rules

Only the following statuses are used during this foundation phase:

- `Pending`: the requirement is described by the available source, but product implementation and verification have not begun.
- `Blocked`: the requirement identifier is known, but its authoritative wording is unavailable.

No row in this document claims that a product feature is implemented, tested, integrated, or complete. Branch names below describe the future ownership workflow only; no branch creation is implied by this document.

## Ownership boundary notes

- Visible UI, frontend interaction, responsive presentation, and frontend socket behavior belong to Domain A.
- Backend logic, persistence, bid ordering, authoritative timing, Socket.IO server behavior, recovery, Redis, and payment verification belong to Domain B.
- A complete feature spanning both domains must be split by responsibility and verified after both future domain branches are merged into `developer`.
- Authentication UI belongs to Domain A; backend authentication and socket authentication belong to Domain B; the complete session flow is shared integration.
- Payment checkout UI belongs to Domain A; winner authorization, order creation, and signature verification belong to Domain B; the complete payment flow is shared integration.
- Timer presentation belongs to Domain A; authoritative timestamps and completion scheduling belong to Domain B; timer synchronization is shared integration.
- Foundation documentation can describe both domains, but it does not transfer future implementation ownership between them.

## Unresolved requirements decisions

The available source does not define the following details. They must be resolved from the missing SRS or recorded as explicit architecture decisions before related feature work begins:

- Minimum-bid formula and increment rules
- Currency and monetary amount unit/precision
- Required auction creation fields and no-bid completion behavior
- Anonymous versus authenticated spectator access
- Presence counting across multiple tabs and reconnect grace periods
- Statistics and auction-heat formulas
- Chat retention, limits, and moderation rules
- Access/refresh token transport and CSRF policy
- Duplicate-request response semantics after a lost acknowledgement
- Mandatory Redis responsibilities, key TTLs, and invalidation policy
- Razorpay webhook, retry, and reconciliation behavior
- Multi-instance bid serialization beyond Socket.IO broadcast coordination

## Reconciliation procedure when the official SRS is available

1. Add the exact official wording and acceptance criteria to every official-ID row.
2. Assign each official requirement to Domain A, Domain B, or Shared integration based on actual responsibility.
3. Link each official identifier to one or more derived requirements rather than relying on ordinal similarity.
4. Add planned implementation and verification references without marking work complete prematurely.
5. Retain `Blocked` for any official requirement whose wording remains missing or ambiguous.
6. Change a status only when repository evidence and the required verification support that change.
